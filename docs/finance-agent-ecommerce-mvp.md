# 电商财务智能体 MVP 设计方案

> 聚焦电商企业的最小可行产品

---

## 一、为什么是电商？

### 1.1 电商财务的核心痛点

电商企业因其业务模式特殊性，比传统企业有更强烈的财务工具需求：

| 痛点 | 传统企业 | 电商企业 |
|------|---------|---------|
| **交易量** | 日均几十笔 | 日均几百~几万笔 |
| **平台数量** | 单一销售渠道 | 3~8 个平台同时经营（淘宝/天猫/京东/拼多多/抖音/跨境等） |
| **收入确认** | 简单，发货即确认 | 复杂：签收确认、7天无理由退货、满减/优惠券/积分 |
| **成本结构** | 较稳定 | 动态剧烈：广告费、平台佣金、直播坑位费、退货损耗 |
| **税务** | 相对标准 | 行业规则复杂：促销计税、刷单税务风险、跨境税务 |
| **对账** | 单一银行流水 | 多平台资金+支付宝/微信+银联，至少每月对账耗时3-5天 |

### 1.2 市场体量

2025 年全国网上零售额超过 **15 万亿**，活跃电商企业超过 **百万级**，其中：
- 年 GMV >1 亿：约 5 万家（腰部及以上）
- 年 GMV 1000 万-1 亿：约 30 万家（典型目标用户）
- 年 GMV <1000 万：大量小微

**目标定位**：年 GMV 1000 万-5 亿的中小型电商企业（1-30 人财务团队，通常 1-3 人）

## 二、MVP 角色定位

### 2.1 一句话价值主张

> **电商财务工作台：自动对账、一键算税、随时看利润。**

### 2.2 核心角色

| 角色 | 日均使用场景 |
|------|------------|
| **电商财务/会计**（核心用户） | 每日花 30 分钟做前一天的**对账+记账+退税** |
| **电商老板/运营负责人**（轻量用户） | 每周打开 2-3 次看仪表盘：**利润、现金流、广告 ROI** |
| **代账会计**（渠道用户） | 每月处理 N 家电商客户的**报税+报表** |

### 2.3 MVP = 电商财务 + 老板看板

不做泛化财务、不做审计模块、不做专业税务筹划、不做多行业适配。

#### P0-1：多维对账引擎（"换个角度就自动对好了"）

这是电商财务最痛的痛点——**没有比这个更痛苦的事了**。

**现状**：财务每月花 3-5 天对账，至少要核对：
1. 平台账单 vs 支付宝/微信/银行流水（资金对账）
2. 平台订单明细 vs 发货系统（业务对账）
3. 平台费用（佣金/广告/服务费）vs 发票（费用对账）

**MVP 方案**：

```
                          ┌───────────────────┐
  数据源导入层             │                   │
                          │  平台账单 (CSV)    │
  用户手动导出上传         │  支付宝流水        │
  或邮件收集              │  微信商户流水       │
                          │  银行流水 (Excel)   │
                          │  发票              │
                          └────────┬──────────┘
                                   ▼
                          ┌───────────────────┐
  匹配引擎                │  自动对账引擎       │
                          │                   │
  配置化匹配规则：          │  ├─ 一对一匹配      │
  - 平台订单金额=银行收款   │  │  (银行流水↔支付宝)│
  - 平台佣金=支付服务费     │  ├─ 多对一匹配      │
  - 含订单号匹配           │  │  (多笔订单↔一笔结算)│
  - 时间窗口匹配(±3天)     │  └─ 模糊匹配        │
                          │  (金额±手续费浮动)   │
                          └────────┬──────────┘
                                   ▼
                          ┌───────────────────┐
  结果呈现                │  ✓ 已匹配 (绿色)    │
                          │  ⚠️ 差异 (黄色)    │
  差异实时展示            │  ✗ 未匹配 (红色)    │
  一键生成差异调节表        │                   │
                          │  差异调节表一键导出   │
                          └───────────────────┘
```

**支持的平台（MVP 阶段）**：

| 平台 | 数据来源 | 导入方式 |
|------|---------|---------|
| 淘宝/天猫 | 千牛账单 | CSV 上传 |
| 京东 | 京东商智 | CSV 上传 |
| 拼多多 | 商家后台 | CSV 上传 |
| 抖音 | 抖店后台 | CSV 上传 |
| 微信小店 | 商户平台 | CSV 上传 |
| 支付宝 | 商家中心 | 流水 CSV |
| 微信 | 商户平台 | 流水 CSV |
| 银行 | 网银 | Excel/CSV |

**不做什么（MVP 阶段）**：
- ❌ 不接 API 自动拉取（各平台开放程度不一，先走文件导入）
- ❌ 不处理跨境平台（Amazon/Shopify 等放后期）
- ❌ 不做实时对账（日结即可）

#### P0-2：收入确认与成本归集

电商的收入确认比传统企业复杂很多，MVP 只做最常用场景。

**收入处理规则**：

| 场景 | 收入确认原则 | MVP 支持？ |
|------|------------|----------|
| 普通销售（签收确认） | 顾客签收后确认收入 | ✅ |
| 7天无理由退货 | 预计退货部分暂不确认 | ✅（按行业退货率预估） |
| 满减/优惠券 | 按实际收入确认 | ✅ |
| 积分兑换 | 分摊至履约义务 | ❌ P2 |
| 跨店满减（天猫） | 按分摊比例 | ❌ P2 |

**成本归集规则**：

```
单个商品的利润 = 
  实收金额（含税）
  - 商品成本（采购/生产）
  - 平台佣金
  - 广告费（按商品分摊）
  - 运费
  - 包装费
  - 退货成本（分摊）
  - 增值税
  = 单品净利润
```

**MVP 实现方式**：

```
用户上传:
  ├─ 平台订单明细 (含商品、金额、佣金、运费)
  └─ 商品采购成本表 (SKU → 成本价)

系统自动计算:
  每笔订单的:
  - 实收 = 订单金额 - 退款 - 优惠
  - 成本 = 商品成本 + 应分摊的广告+运费
  - 毛利润 = 实收 - 成本
  - 毛利率 = 毛利润 / 实收
```

#### P0-4：增值税计算与申报辅助

电商企业增值税的特殊性：

| 纳税人类型 | 税率 | 特殊规则 |
|-----------|------|---------|
| 一般纳税人-自营 | 13% | 全额计税，进项可抵扣 |
| 一般纳税人-平台 | 6% | 平台服务费税率 |
| 小规模纳税人 | 3%（减按1%） | 全额计税，不可抵扣 |

**MVP 功能**：

```
# 增值税计算器

输入：
  纳税人类型: [一般纳税人/小规模纳税人]
  本期销售收入（含税）: ¥______
  其中: 自营 (13%) ¥_   平台服务 (6%) ¥_   其他 ¥_
  进项发票金额（含税）: ¥______
  出口销售额: ¥______ (如有)

输出：
  ┌──────────────────────────────────────────┐
  │  增值税计算明细                             │
  │                                            │
  │  销项税额: ¥1,380,000 × 13% = ¥179,400    │
  │  进项税额: ¥800,000 × 13% = ¥104,000      │
  │  ─────────────────────────────────         │
  │  **应纳增值税: ¥75,400**                   │
  │                                            │
  │  附加税: ¥75,400 × 12% × 50% = ¥4,524     │
  │  (小规模纳税人附加税减半)                    │
  │                                            │
  │  💡 建议: 当前进项占比76%, 行业平均为65%,   │
  │     进项抵扣较为充分。建议核对是否有可抵扣    │
  │     但未及时取得发票的进项项目。             │
  └──────────────────────────────────────────┘
```

**MVP 不做**：
- ❌ 不自动对接电子税务局（各平台接口差异大）
- ❌ 不做企业所得税计算（每年一次，复杂度过高）
- ❌ 不做发票管理（标准化产品太多，不做重复轮子）

#### P0-5：资金对账（出纳视角）

电商企业的资金流比普通企业复杂 3~5 倍：

```
订单收款
  ├─ 支付宝 → 对公账户
  ├─ 微信支付 → 微信商户 → 提现到对公
  ├─ 银行卡 → 直接到账
  ├─ 分期/花呗 → 平台结算周期后到账
  └─ 跨境收款 → 连连/PingPong → 结汇后到对公

支出项
  ├─ 平台扣费 (佣金/广告/技术服务费/保证金)
  ├─ 采购付款 (原材料/成品/包材)
  ├─ 物流费用 (快递费/仓储费)
  ├─ 工资/社保
  └─ 其他经营费用
```

**MVP 功能**：

## 四、MVP 数据架构

### 4.1 电商专属数据模型

```typescript
// 核心电商数据类型

// 店铺 (每个平台一个店铺)
interface Shop {
  id: string;
  name: string;            // 店铺名称
  platform: 'taobao' | 'tianmao' | 'jd' | 'pdd' | 'douyin' | 'kuaishou' | 'weixin' | 'amazon' | 'other';
  accountSetId: string;    // 对应哪个账套
  platformShopId: string;  // 后台店铺ID
  credentials: string;     // 加密的登录凭证 (如有)
  createdAt: string;
}

// 平台订单
interface PlatformOrder {
  id: string;
  shopId: string;
  platformOrderNo: string; // 平台订单号
  createdTime: string;
  payTime: string;
  confirmTime: string;     // 签收时间（收入确认时点）
  status: 'pending' | 'paid' | 'shipped' | 'confirmed' | 'refunding' | 'refunded' | 'cancelled';
  totalAmount: number;
  discountAmount: number;
  netAmount: number;       // 实收
  shippingFee: number;
  buyerMessage: string;
  items: OrderItem[];
  refundStatus?: RefundInfo;
}

interface OrderItem {
  skuId: string;
  productName: string;
  quantity: number;
  unitPrice: number;
  costPrice: number;       // 成本价（从成本表匹配）
  commission: number;       // 佣金
  adCost: number;          // 广告费分摊
}

// 平台账单 (资金对账用)
interface PlatformBill {
  id: string;
  shopId: string;
  billDate: string;
  transactions: Transaction[];
  // 平台扣费汇总
  totalCommission: number;
  totalAdCost: number;
  totalServiceFee: number;
  totalRefund: number;
  netSettlement: number;   // 实际结算到账
}

// 匹配结果
interface ReconciliationResult {
  id: string;
  orderId: string;
  billId: string;
  bankTransactionId: string;
  status: 'matched' | 'partial' | 'unmatched';
  expectedAmount: number;
  actualAmount: number;
  difference: number;
  matchRule: string;       // 匹配规则名称
}
```

### 4.2 电商特有指标

```typescript
interface EcommerceMetrics {
  // 核心交易指标
  gmv: number;                   // 总成交额
  netRevenue: number;            // 净收入 (GMV - 退款 - 优惠)
  orderCount: number;
  averageOrderValue: number;     // 客单价
  
  // 成本指标
  totalCost: number;             // 商品总成本
  fulfillmentCost: number;       // 履约成本 (运费+包装)
  marketingCost: number;         // 营销费 (广告+直播坑位+佣金)
  platformFee: number;           // 平台费用
  
  // 利润指标
  grossProfit: number;           // 毛利 = 净收入 - 商品成本
  grossMargin: number;           // 毛利率
  netProfit: number;             // 净利 = 毛利 - 营销费 - 平台费 - 管理费
  netMargin: number;             // 净利率
  
  // 运营指标
  refundRate: number;            // 退款率

## 六、AI 能力在 MVP 中的角色

### 6.1 MVP 中 AI 的主要职责

| 场景 | AI 能力 | 实现方式 |
|------|--------|---------|
| **导入字段映射** | 自动识别各平台 CSV 的列名 | 规则匹配 + LLM 兜底 |
| **异常预警解读** | 分析毛利率下降原因 | LLM 结构化输出 |
| **对账差异辅助判断** | "这笔 0.5 元差异是手续费" | LLM 推理 |
| **成本分摊建议** | "广告费应按店铺按商品分摊比例是…" | 规则 + LLM 解释 |
| **经营建议** | 每周自动生成一份"老板周报" | LLM 生成自然语言 |

### 6.2 MVP 不依赖 LLM 的能力

| 能力 | 实现方式 | 为何不依赖 LLM |
|------|---------|---------------|
| 对账匹配 | 确定性规则引擎 | 金额+订单号就是确定性匹配 |
| 增值税计算 | Python 计算公式 | 精确计算，不允许幻觉 |
| 毛利率计算 | pandas 聚合计算 | 纯数学运算 |
| 报表生成 | Jinja2 模板 | 固定的格式化需求 |

### 6.3 LLM 介入的成本控制

MVP 阶段 LLM 调用量可控：

```
每天调用量估算 (1 个活跃用户):
  导入字段映射: ~5 次 (每个文件)
  异常解读: ~3 次 (每天)
  老板周报: ~1 次 (每周)
  → 日均 ~10 次 LLM 调用

每次用 gpt-4o-mini 或本地 qwen2.5-7b:
  输入: ~2000 tokens
  输出: ~500 tokens
  费用: ~$0.001/次
  日均: ~$0.01/用户
```

## 九、AI 智能助手在 MVP 中的角色

虽然 MVP 以确定性引擎为核心，但 AI 智能助手（基于 Hermes Agent）在两个场景中发挥关键作用：

### 9.1 数据导入阶段的 AI 自适应

不同电商平台导出的 CSV 格式经常变化（字段名改了、顺序变了），LLM 在此做**自适应解析**：

```
用户上传 "天猫结算账单_20260706.csv"
    │
    ▼
┌──────────────────────────────────────────────┐
│  规则引擎解析                                  │
│  → 尝试按预设模板匹配                          │
│  → 匹配度 65% (字段名有变化)                    │
│  → 触发 LLM 兜底                               │
└──────────────────────┬───────────────────────┘
                       ▼
┌──────────────────────────────────────────────┐
│  LLM 自适应映射                                │
│                                              │
│  Prompt: "这是一个电商结算账单CSV. 请分析      │
│  每列的语义, 映射到标准字段: order_id,         │
│  pay_time, product_name, amount, commission,  │
│  refund, status.                              │
│  CSV 列名: [订单编号, 成交时间, 商品,          │
│  实付金额, 佣金, 退款金额, 订单状态]"          │
│                                              │
│  输出: {order_id: "订单编号", ...}             │
└──────────────────────┬───────────────────────┘
                       ▼
              新模板自动保存到模板库
              下次同类文件直接匹配
```

### 9.2 对话式数据洞察

在利润分析页面嵌入 AI 对话：

```
用户: "为什么天猫渠道毛利率上个月24%，这个月只有19%？"

智能体执行链路:
  ① 查询天猫店铺上个月和这个月的利润数据
  ② 按品类拆分毛利率变化
  ③ 计算各品类毛利率变化贡献度
  ④ 发现: "连衣裙品类毛利贡献下降最大，从+8万降到-2万"

  → 回复:
  "天猫毛利率下降主要受连衣裙品类影响:
  1. 该品类毛利率从 32% 降至 15%
  2. 退货率从 18% 升至 35%
  3. 广告费占比从 8% 升至 15%
  
  建议: ① 检查连衣裙的尺码描述是否准确(退货率突升)
        ② 评估广告投放效率(ACOS 是否过高)
        ③ 考虑是否要调整该品类的定价策略"

用户: "帮我算一下如果连衣裙降价10%，毛利率会变成多少？"

智能体:
  → 假设降10%后销量增加20%，退货率不变
  → 快速计算: 降价后毛利率约 8%(从15%降至)
  → 建议不一定降价，建议优化广告投放和退货。
```

          │                    │

          │   (电商 × 财务)    │
          │                    │
  通用 ───┤                    ├─── 电商垂直
  财务    │     用友/金蝶       │
          │                    │
          └──── 弱自动化 ────┘

FinSight MVP 的优势:
  - 电商行业财务深度：比用友/金蝶更懂电商对账、电商利润
  - AI 原生：比传统财务软件更低的交互门槛、自动适配
  - 轻盈：Tauri 桌面端 VS 传统 ERP 的厚重客户端
```

## 十三、关键风险

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| 各平台账单格式频繁变更 | 高 | 高 | 导入引擎 + LLM 自适应兜底，模板库可热更新 |
| 电商企业经营数据敏感性 | 中 | 高 | 全部数据本地存储，不上传；开源核心逻辑 |
| 对账匹配准确率不够 | 中 | 中 | MVP 阶段不追求100%自动匹配（95%+），剩余人工处理 |
| 用户不愿意手动导出上传 | 中 | 中 | 先做文件导入验证价值，再逐步自动化拉取 |
| 电商企业付款意愿/能力 | 中 | 高 | MVP 阶段免费开放，收集反馈；后续按店铺数/订单量收费 |
| 数据量大时性能下降 | 中 | 中 | 按日期范围查询，本地 SQLite 百万级数据足够 |

## 十五、如何衡量 MVP 成功

| 指标 | 目标值 | 测量方式 |
|------|-------|---------|
| 核心流程完成率 | >90% | 用户从导入到完成对账的成功率 |
| 自动匹配率 | >95% | 成功自动匹配的订单比例 |
| 用户使用留存 (7日) | >70% | 安装后 7 天内再次打开的比例 |
| 日均使用时长 | >15 分钟 | 用户每天的活跃时间 |
| 对账时间节省 | >70% | 原来 2-3 天/月 → ≤0.5 天/月 |
| NPS (净推荐值) | >30 | 内测用户满意度调研 |
