### 能力 #1 · 智能文档分类

> "自动识别并分类财务文档（合同、发票、银行对账单），关联至对应会计科目"

| 项目 | 方案 |
|------|------|
| **所属层** | 文档引擎（Document Engine） |
| **核心组件** | OCR + 文档分类模型 + 科目映射规则 |
| **实现路径** | 3 层管道：识别 → 分类 → 关联 |

#### 实现架构

```
用户上传文档
    │
    ▼
┌─────────────────────────────────┐
│ Layer 1: 文档识别层              │
│                                 │
│  PDF/图片 → PaddleOCR (文字提取) │
│  Excel/CSV → openpyxl (直接解析) │
│  Word → python-docx             │
│  扫描件 → PaddleOCR + 版面分析   │
│                                 │
│  输出: 结构化文本 + 元信息        │
└────────────┬────────────────────┘
             ▼
┌─────────────────────────────────┐
│ Layer 2: 文档分类层              │
│                                 │
│  规则引擎 (关键字+模板匹配):      │
│  ├─ "增值税专用发票" "发票代码" → │
│  │   增值税发票                  │
│  ├─ "银行回单" "交易日期" →      │
│  │   银行对账单                  │
│  ├─ "合同" "甲方" "乙方" →      │
│  │   合同                       │
│  └─ "工资表" "考勤" →           │
│       工资单                     │
│                                 │
│  LLM 兜底分类 (规则不命中时):     │
│  "请判断此文档类型并给出置信度"    │
│                                 │
│  输出: {type, subtype, confidence}│
└────────────┬────────────────────┘
             ▼
┌─────────────────────────────────┐
│ Layer 3: 科目关联层              │
│                                 │
│  规则引擎 (文档类型 → 科目映射):  │
│  ├─ 增值税专用发票(采购) →       │
│  │   借: 原材料/库存商品          │
│  │   借: 应交税费-应交增值税(进项)│
│  ├─ 银行回单(利息) →             │
│  │   借: 银行存款                │
│  │   贷: 财务费用-利息收入        │
│  ├─ 差旅发票 →                  │
│  │   借: 管理费用-差旅费          │
│  └─ 合同(收入) →                │
│      借: 应收账款                │
│      贷: 主营业务收入             │
│                                 │
│  LLM 辅助 (复杂场景):            │
│  "根据发票内容和公司科目表，推荐  │
│  最合适的借贷科目，给出理由"       │
│                                 │
│  输出: {debitAccount, credit    │
│         Account, amount, memo}  │
└────────────┬────────────────────┘
             ▼
    用户确认/修改 → 生成凭证草稿
```

#### 关键技术决策

- **优先规则引擎，LLM 兜底**：文档分类 80% 以上可以靠模板匹配解决，只有边界案例才调 LLM。这比全量 LLM 方案成本低 100 倍、延迟低 10 倍。
- **PaddleOCR 优于云端 OCR**：财务数据敏感，必须在本地处理。PaddleOCR 在中文场景精度已超 95%，且支持 GPU 加速。
- **Lark 所说的"60%效率提升"** 来源：一个律师/财务人员每天花 1-2 小时分类文档和写凭证摘要这条链路，自动化后这部分时间归零。

#### 关联能力

与 **#13（OCR 发票提取）** 共享底层 OCR 管道，差异在输出端：#13 输出结构化字段（商品名、金额、税率），#1 在此基础上做分类和科目关联。

### 能力 #13 · 智能发票提取

> "自动提取发票中的商品名称、金额、税率等信息，生成凭证"

| 项目 | 方案 |
|------|------|
| **所属层** | 文档引擎—发票提取子模块 |
| **核心组件** | 发票专用 OCR 模型 + 结构化提取模板 + 直连税局查验 |

#### 实现架构

```
发票文件 (PDF/图片)
    │
    ▼
┌─────────────────────────────┐
│ Step 1: 发票识别             │
│                             │
│  ① 版面检测 (PaddleOCR):    │
│     识别发票中的表格区域      │
│  ② 字段提取 (规则+ML):      │
│     - 发票代码/号码          │
│     - 开票日期               │
│     - 购买方/销售方信息       │
│     - 商品明细 (名称/数量    │
│       /单价/金额/税率/税额)  │
│     - 合计金额/税额/价税合计  │
│     - 校验码                 │
│                             │
│  ③ 特殊处理:                 │
│     - 全电发票 (XML解析)     │
│     - 卷式发票               │
│     - 通行费电子发票          │
│     - 火车票/机票行程单       │
└────────────┬────────────────┘
             ▼
┌─────────────────────────────┐
│ Step 2: 真伪查验 (可选)      │
│                             │
│  MCP → 国家税务总局发票查验  │
│  平台 (需用户授权):          │
│  校验结果: 正常/不一致/查无 │
│  此发票                     │
└────────────┬────────────────┘
             ▼
┌─────────────────────────────┐
│ Step 3: 凭证生成             │
│                             │
│  规则引擎 (根据发票类型+      │
│  企业科目表):                │
│                             │
│  采购发票:                   │
│  借: 原材料/库存商品          │
│  借: 应交税费-进项税额       │
│  贷: 应付账款/银行存款        │
│                             │
│  费用发票:                   │
│  借: 管理费用-XX费           │
│  贷: 银行存款/其他应付款     │
│                             │
│  输出: 凭证草稿 (待审核)      │
└────────────┬────────────────┘
             ▼
    用户确认 → 同步至 ERP
```

#### 为什么能做到"2小时→10分钟"

| 环节 | 手工 (分钟/天) | AI 辅助 (分钟/天) |
|------|--------------|-----------------|
| 发票整理/扫描 | 20 | 2 (批量扫描) |
| 逐张录入科目 | 40 | 2 (自动推荐) |
| 核对金额/税额 | 30 | 1 (自动比对) |
| 生成凭证 | 20 | 3 (生成+确认) |
| 归档 | 10 | 2 (自动归档) |
| **合计** | **120** | **10** |

#### 技术选型说明

- **为什么用 MCP 协议做连接器？** LawClaw 已证明 MCP 是标准化的工具接入协议，每个 ERP 连接器就是一个 MCP Server，可独立开发、部署、维护。
- **离线优先**：财务数据同步到本地 SQLite/DuckDB，驾驶舱在本地渲染，无需持续联网。

#### "审计整改效率提升 60%"的来源

```
传统流程的问题：
  手工录入 → 科目用错 → 月末调账 → 审计发现 → 补凭证 → 整改
                                                      ↑
                                                 这一整条链路
FinSight 流程：
  ERP 数据 → 规则引擎 → 凭证生成 → 实时校验 → 审计可查
                                                 ↑
                                             问题前置解决

60% 效率提升 = 
  (手工录入错误减少) + (月末调账减少) + (审计发现减少)
```

### 能力 #5 · 智能申报

> "自动生成增值税、企业所得税等申报表，直连电子税务局"

| 项目 | 方案 |
|------|------|
| **所属层** | 应用服务层 — 申报引擎 |
| **核心组件** | 税表计算器 + 申报表模板 + 电子税务局 MCP 连接器 |

#### 实现架构

```
┌────────────────────────────────────────────┐
│          数据准备层                         │
│                                            │
│  从 ERP/账套 提取:                         │
│  - 科目余额表 (各科目借方/贷方累计)          │
│  - 发票数据 (销项/进项汇总)                 │
│  - 固定资产折旧表                          │
│  - 工资表 (个税计算基础)                    │
│  - 预缴税款记录                            │
└──────────────────┬─────────────────────────┘
                   ▼
┌────────────────────────────────────────────┐
│          计算引擎层                         │
│                                            │
│  RPC 技能 (非 LLM，纯 Python 计算):         │
│                                            │
│  增值税申报计算:                            │
│  - 销项税额 = 应税销售额 × 适用税率          │
│  - 进项税额 = 认证抵扣 + 计算抵扣            │
│  - 进项转出 = 非应税项目/集体福利等          │
│  - 应纳税额 = 销项 - 进项 + 进项转出 - 留抵  │
│                                            │
│  企业所得税申报:                            │
│  - 会计利润 → 纳税调增/调减                  │
│  - 应纳税所得额 = 会计利润 ± 调整项          │
│  - 应纳所得税额 = 应纳税所得额 × 税率        │
│  - 减免税额/抵免税额                        │
│                                            │
│  输出: 申报表数据 (结构化 JSON)              │
└──────────────────┬─────────────────────────┘
                   ▼
┌────────────────────────────────────────────┐
│          申报表生成层                       │
│                                            │
│  申报表模板引擎 (Jinja2/ReportLab):         │
│  ├─ 增值税申报表 (主表 + 附表 1-5)          │
│  ├─ 企业所得税预缴表 (A类/B类)              │
│  ├─ 个税扣缴申报表                          │
```

#### "准确率 85% → 99%" 的来源

```
传统模式: 人工从 ERP 导出数据 → 手动填入申报表 → 算错 → 更正
                                  ↓
                           人为错误 (税率选错
                           数字填反、逻辑校验漏)

  - 税率适用: 行业 × 商品类别交叉校验
  - 税负率: 行业平均 vs 企业历史 vs 当前
  - 趋势异常: 环比/同比增长 > 30% 预警
```

```
  IF 库存周转率 < 行业基准 × 0.7 AND 库龄 > 90天:
    标记为 "滞销风险"
    推送: "XX商品已入库120天，库存周转率仅为行业
           的50%，建议: ① 促销清库存; ② 暂停补货"

效果:
  第1周 → 识别滞销品清单 → 业务部门评估
  第2周 → 促销/退货处理 → 库存下降
  第N周 → 持续监测 → 滞销率从15%降至8%
```

### 能力 #9 · 实时财务数据

> "提供烧钱率、现金流、运营成本等关键指标"

| 项目 | 方案 |
|------|------|
| **所属层** | Dashboard + 监控引擎 |
| **核心组件** | 实时 KPI 计算组件 |

#### 关键指标定义

| 指标 | 计算公式 | 更新频率 | 目标用户 |
|------|---------|---------|---------|
| **烧钱率 (Burn Rate)** | `(期初现金 - 期末现金) / 天数` | 每日 | 创业公司/CFO |
| **Runway** | `期末现金 / 日均烧钱率` | 每日 | 同上 |
| **经营性现金流** | `经营流入 - 经营流出 (期间)` | 每周 | CFO |
| **净营运资金** | `流动资产 - 流动负债` | 每周 | 财务经理 |
| **运营成本** | `销售费用+管理费用+研发费用` | 每月 | 管理层 |
| **EBITDA** | `净利润+利息+折旧+摊销` | 每月 | 投资者/CFO |
| **单位经济学** | `LTV / CAC` | 每月 | 互联网公司CFO |

#### 实现

这些指标直接从已同步的 ERP 数据计算，无需 LLM：

```python
# RPC 技能: key_metrics
def calculate_burn_rate(cash_balance_history: list[dict]) -> dict:
    """计算烧钱率"""
    recent = cash_balance_history[-30:]  # 近30天
    total_days = len(recent) - 1
    total_burn = recent[0]['balance'] - recent[-1]['balance']
    daily_burn = total_burn / total_days if total_days > 0 else 0
    runway = recent[-1]['balance'] / daily_burn if daily_burn > 0 else float('inf')
    
    return {
        "daily_burn_rate": round(daily_burn, 2),
        "monthly_burn_rate": round(daily_burn * 30, 2),
        "runway_days": round(runway),
        "runway_months": round(runway / 30, 1),
        "trend": "increasing" if daily_burn > 0 else "decreasing"
    }
```

### 关键设计原则

从这 13 项能力的分析可以提炼出三条架构原则：

**原则 1：RPC 做计算，LLM 做理解**
- 税率计算、申报表填列、指标计算 → Python 计算引擎
- 政策解读、差异分析、优化建议 → LLM 生成
- 这条界限划得越清晰，系统越可靠

**原则 2：规则引擎兜住 80%，LLM 处理 20% 边界**
- 文档分类、科目映射、异常检测 → 先用规则
- 规则覆盖不到的模糊场景 → LLM 兜底
- 这确保了成本和延迟可预期

**原则 3：本地优先，云端可选**
- OCR、文档分析、数据计算 → 本地（PaddleOCR + pandas）
- 政策 RAG → 本地向量库
- LLM 推理 → 可选本地（ollama）或云端（兼容 OpenAI API）
- 财务数据永远不出本地边界
