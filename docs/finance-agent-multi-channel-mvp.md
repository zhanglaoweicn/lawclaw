# 电商 MVP 方案补充：多渠道混合业务场景

> 中小电商企业 = 线上平台 + 私域自营 + 线下批发 + 线下零售 的混合体

---

## 一、典型企业画像

### 1.1 一家典型的"混合渠道"电商企业

```
XX 食品有限公司
├── 员工: 85 人
├── 年营收: ¥8000 万
│
├── 📱 线上平台 (60%)
│   ├── 天猫旗舰店 (25%)      → 年 ¥2000 万
│   ├── 京东自营 (10%)        → 年 ¥800 万
│   ├── 抖音店铺 (15%)        → 年 ¥1200 万
│   └── 视频号小店 (10%)      → 年 ¥800 万
│
├── 💬 私域自营 (15%)
│   ├── 微信小程序商城 (10%)   → 年 ¥800 万
│   └── 企业微信+社群团购 (5%) → 年 ¥400 万
│
├── 🏭 线下批发 (15%)
│   ├── 经销商 (10%)          → 年 ¥800 万
│   └── 大客户定制 (5%)       → 年 ¥400 万
│
└── 🏪 线下零售 (10%)
    ├── 直营门店 ×3 (6%)      → 年 ¥480 万
    └── 经销商门店供货 (4%)   → 年 ¥320 万
```

### 1.2 这家企业财务人员的日常工作

```
每月初，财务小张要完成：

📱 线上平台 (耗时 3 天)
  ├─ 天猫：导出结算单 → 逐笔核对支付宝 → 核对银行到账
  ├─ 京东：京东钱包结算 → 核对银行到账
  ├─ 抖音：抖店账单 → 核对银行卡流水
  └─ 视频号：视频号小店账单 → 核对微信商户

💬 私域自营 (耗时 1 天)
  ├─ 小程序：微信商户后台导出 → 核对银行到账
  └─ 群团购：微信转账记录逐笔登记 → 手工做账

🏭 线下批发 (耗时 1.5 天)
  ├─ 对账：给经销商发对账单 → 催款
  ├─ 开票：根据回款开票
  └─ 账期管理：跟踪各经销商的应收账款账龄

🏪 线下零售 (耗时 0.5 天)
  ├─ 各门店销售日报汇总
  ├─ 门店费用报销
  └─ 门店库存盘点差异

📊 全渠道汇总 (耗时 2 天)
  └─ 把以上四个渠道的数据统一到一个利润表里
    →  不同渠道的报表格式完全不同
    →  全渠道毛利率 = ?
    →  本月整体是赚是亏?

📋 税务 (耗时 1 天)
  └─ 汇总所有渠道的销售额 → 算增值税

合计：约 9 天/月
```

### 1.3 核心痛点排序

| 排名 | 痛点 | 来源于 | 当前做法 |
|------|------|--------|---------|
| 🥇 | **多渠道对账繁琐** | 各平台+银行+微信+支付宝混在一起 | 手工逐笔核对 |
| 🥇 | **全渠道利润算不清** | 各渠道成本结构不同，难以合并 | 简单加总，不准 |
| 🥇 | **应收账款管理难** | 批发客户账期不同，经常忘了催 | 手工台账 |
| 🥈 | **进销存和财务脱节** | 库存系统一套，财务系统一套 | 月末对账，差异大 |
| 🥈 | **税务申报数据分散** | 各渠道数据散落，汇总易错 | 手工汇总 |
| 🥉 | **老板决策没数据** | 想看"到底哪个渠道赚钱"说不清 | 凭感觉 |

## 二、多渠道统一数据模型

### 2.1 核心设计思想

**四条渠道，一套模型；数据口径统一，分渠道核算。**

所有业务渠道（线上平台/私域自营/线下批发/线下零售）最终都抽象为：

```
每一笔业务 = 
  {渠道, 时间, 商品, 数量, 金额(多维度), 客户, 资金流, 费用}
```

### 2.2 渠道类型定义

```typescript
type ChannelType = 
  | 'platform'           // 线上平台 (天猫/京东/抖音/视频号/拼多多)
  | 'private_domain'     // 私域自营 (小程序/社群/APP/微店)
  | 'wholesale'          // 线下批发 (经销商/大客户/OEM)
  | 'retail'             // 线下零售 (直营门店/专柜/加盟店)
  | 'other';             // 其他 (零星/员工内购/赠品等)
```

### 2.3 统一交易模型

```typescript
// === 核心：统一交易记录 ===
interface UnifiedTransaction {
  id: string;
  accountSetId: string;
  
  // —— 渠道信息 —
  channel: ChannelType;
  channelSource: string;    // 具体来源：如 "tianmao", "wechat_miniapp", "dealer_001", "store_beijing"
  
  // —— 业务信息 —
  transactionDate: string;  // 业务日期
  transactionType: 'sale' | 'refund' | 'expense' | 'transfer' | 'adjustment';
  
  // —— 商品维度 —
  items: TransactionItem[]; // 商品明细（所有渠道都统一到这一层）
  
  // —— 金额维度（最关键的设计）—
  // 根据渠道不同，部分字段可能为0，但口径统一
  amounts: {
    // ① 销售端
    grossAmount: number;       // 含税总价 (标价总和)
    discountAmount: number;    // 优惠/折扣金额
    netAmount: number;         // 实收金额 (gross - discount)
    refundAmount: number;      // 退款金额
    
    // ② 平台费用 (仅线上平台)
    platformCommission: number; // 平台佣金
    platformAdCost: number;     // 平台广告费
    platformServiceFee: number; // 平台技术服务费等
    platformOtherFee: number;   // 其他平台扣费
    
    // ③ 支付费用 (全渠道，但线上为主)
    paymentFee: number;         // 支付手续费
    
    // ④ 物流费用
    shippingFee: number;        // 运费 (由商家承担的)
    
    // ⑤ 资金端
    settledAmount: number;      // 实际结算到账金额 (net - 平台费 - 支付费 - 运费)
  };
  
  // —— 客户维度 —
  customer?: {
    id: string;
    name: string;
    type: 'individual' | 'dealer' | 'corporate';  // 个人/经销商/企业客户
  };
  
  // —— 资金流维度 —
  fundFlow: {
    paymentMethod: 'alipay' | 'wechat' | 'bank_transfer' | 'cash' | 'card' | 'credit' | 'other';
    bankAccountId: string;     // 入账银行账户
    settlementDate?: string;   // 资金到账日期（滞后于交易日期）
    settlementStatus: 'pending' | 'settled' | 'discrepancy';
  };
  
  // —— 发票维度 (批发场景关键) —
  invoice?: {
    required: boolean;
    issued: boolean;
    invoiceNumber?: string;
    invoiceAmount?: number;
    invoiceDate?: string;
  };
  
  // —— 账期维度 (批发场景关键) —
  credit?: {
    term: number;              // 账期天数
    dueDate: string;           // 应付款日期
    paidDate?: string;         // 实际付款日期
    overdueDays?: number;      // 逾期天数
  };
  
  // —— 库存维度 —
  inventoryImpact: {
    productId: string;
    warehouseId: string;
    quantity: number;           // 正为出库，负为入库(退货)
    costAmount: number;         // 出库成本（用于计算毛利）
  };
}

// 商品明细
interface TransactionItem {
  productId: string;
  productName: string;
  sku: string;
  quantity: number;
  unitPrice: number;            // 销售单价
  costPrice: number;            // 成本单价
  subTotal: number;             // 小计金额
}
```

### 2.4 四条渠道的数据形态差异与统一

| 维度 | 📱 线上平台 | 💬 私域自营 | 🏭 线下批发 | 🏪 线下零售 |
|------|------------|------------|------------|------------|
| **数据来源** | 平台结算单 | 微信商户/自有商城后台 | 销售合同+对账单+回单 | POS系统+收银流水 |
| **交易频率** | 高（日千笔） | 中（日百笔） | 低（月几十笔） | 中（日几百笔） |
| **收入确认** | 签收确认（有退货期） | 发货确认或签收确认 | 按合同（发货/验收） | 收款即确认 |
| **费用结构** | 佣金+广告+技术服务费等多达10+项 | 支付手续费为主 | 销售费用+物流 | 租金+人工+水电 |
| **资金到账** | T+1 ~ T+15（平台结算周期） | T+1（微信/支付宝） | 账期 30-90天 | 实时到账 |
| **应收账款** | 无（平台代收） | 无 | **核心痛点**：账期管理 | 极少 |
| **发票需求** | 消费者不要票居多 | 同上 | **客户必须开票** | 少量要票 |
| **退款/退货** | 频繁，有平台规则 | 较少 | 极少（按合同） | 较少 |
| **匹配逻辑** | 平台订单号 ↔ 支付流水 ↔ 银行到账 | 微信支付订单号 ↔ 银行 | 对账单金额 ↔ 回单金额 ↔ 发票 | POS汇总 ↔ 银行收款 |

### 2.5 各渠道的收入确认规则

不同渠道的收入确认时点不同，直接影响报表准确性：

```
📱 线上平台
  ├─ 消费者下单付款 → 不计收入（在途）
  ├─ 商家发货 → 不计收入（在途）
  ├─ 消费者签收 → ✅ 确认收入
  └─ 退货期内 → 按退货率计提预计负债

💬 私域自营
  ├─ 顾客下单付款 → ✅ 确认收入（无平台退货机制）
  └─ 发生退货时 → 冲减收入

🏭 线下批发
  ├─ 按合同约定: 发货/签收/验收三种时点
  └─ 典型: 客户签收 → ✅ 确认收入

🏪 线下零售
  └─ 顾客付款 → ✅ 立即确认收入
```

**MVP 简化策略**：让用户在设置中选择各渠道的收入确认规则，系统按规则自动计算。

## 三、MVP 核心功能扩展

### 3.1 多渠道对账引擎（扩展版）

原型中只做了"平台订单 vs 资金"的一维对账，现在要扩展到**四类渠道四种对账模式**：

```
                      ┌──────────────────────────────────┐
                      │         统一对账入口               │
                      │                                  │
                      │  [渠道筛选: 全部/线上/私域/批发/零售]│
                      │  [日期范围] [开始对账]             │
                      └──────────┬───────────────────────┘
                                 │
         ┌───────────────────────┼───────────────────────┐
         ▼                       ▼                       ▼
┌─────────────────┐   ┌─────────────────┐   ┌─────────────────┐
│ 📱 线上平台对账   │   │ 💬 私域对账      │   │ 🏭 批发对账      │
│                 │   │                 │   │                 │
│ 平台结算单       │   │ 微信商户流水     │   │ 销售合同/订单    │
│    ↕ 匹配        │   │    ↕ 匹配        │   │    ↕ 匹配        │
│ 支付宝/微信流水   │   │ 银行流水(到账)   │   │ 银行回单(回款)   │
│    ↕ 匹配        │   │                 │   │    ↕ 匹配        │
│ 银行到账         │   │ 自有商城订单明细  │   │ 开票记录         │
│                 │   │                 │   │                 │
│ 差异提示:        │   │ 差异提示:        │   │ 差异提示:        │
│ 平台扣费/退款/   │   │ 支付手续费差异   │   │ 逾期未回款/      │
│ 结算周期差异      │   │                 │   │ 发票未开         │
└─────────────────┘   └─────────────────┘   └─────────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │ 🏪 零售对账              │
                    │                         │
                    │ POS 日报汇总              │
                    │    ↕ 匹配                │
                    │ 银行收款/扫码收款汇总     │
                    │                         │
                    │ 差异提示:                 │
                    │ POS金额vs实际到账/现金差异│
                    └─────────────────────────┘
```

#### 线上平台对账（MVP 已有，精细化）

```
输入: 平台结算单 + 支付流水 + 银行流水

匹配三元组:
  (平台订单号, 支付单号, 银行流水号)

输出:
  ┌──────────────────────────────────────────────┐
  │  ✅ 完全匹配: 三单一致                        │
  │  ⚠️ 金额差异: 平台金额 ≠ 银行到账（手续费等） │
  │  ❌ 平台有,银行无: 结算中/退单已扣            │
  │  ❌ 银行有,平台无: 其他来源入账               │
  └──────────────────────────────────────────────┘
```

#### 私域自营对账（新增）

```
输入: 小程序订单 + 微信商户流水 + 银行流水

特殊处理:
  - 微信商户流水 vs 银行入账：T+1到账，金额一致
  - 差异几乎只有支付手续费 0.6%
  - 若有多个小程序/社群，需区分到各收入来源

输出:
  ┌──────────────────────────────────────────────┐
  │  ✅ 订单金额 = 银行入账 + 手续费              │
  │  ⚠️ 手续费差异: 费率不符                     │
  │  ❌ 订单有,银行无: 提现未到账                 │
  └──────────────────────────────────────────────┘
```

#### 线下批发对账（新增——这是最大增量）

```
输入: 销售合同/订单 + 对账单 + 银行回单 + 开票记录

对账逻辑（非逐笔，按单/按批次）:
  ① 销售单金额 vs 回款金额 → 差异显示
  ② 回款期限 vs 实际回款日期 → 逾期天数计算
  ③ 开票情况追踪 → 已回款未开票提醒

输出:
  ┌──────────────────────────────────────────────┐
  │  客户对账单                                   │
  │                                              │
  │  XX经销商  ████████████ 逾期 15 天           │
  │  ┌──────┬────────┬──────┬──────┬────────┐   │
  │  │ 日期  │ 订单号  │ 金额  │ 已回款 │ 欠款   │   │
  │  │ 6/01  │ PO-001  │ 5万   │ 5万   │ 0     │   │
  │  │ 6/15  │ PO-002  │ 8万   │ 0     │ 8万 ⚠️│   │
  │  │ 6/20  │ PO-003  │ 3万   │ 0     │ 3万 🔴│   │
  │  ├──────┼────────┼──────┼──────┼────────┤   │
  │  │ 合计  │        │ 16万  │ 5万   │ 11万   │   │
  │  └──────┴────────┴──────┴──────┴────────┘   │
  │                                              │
  │  [生成对账单发送给客户]  [批量催款]           │
  └──────────────────────────────────────────────┘
```

#### 线下零售对账（新增）

```
输入: POS日报 + 收款汇总

对账逻辑:
  POS销售汇总 → 应收 = 微信 + 支付宝 + 现金 + 银行卡
  银行实际到账 → 微信商户 + 支付宝商户 + 银行对公

差异来源:
  - 手续费 (POS费率 0.38%-0.6%)
  - 到账延迟 (T+1)
  - 现金差异 (长短款)

输出:
  ┌──────────────────────────────────────────────┐
  │  门店日报对账                                 │
  │                                              │
  │  北京店 | 2026-07-07                         │
  │  ┌──────────────────────────────────────┐    │
  │  │ 收款方式  │ POS记录 │ 实际入账 │ 差异  │    │
  │  │ 微信      │ 12,500  │ 12,420  │ -80   │    │
  │  │ 支付宝    │ 8,200   │ 8,150   │ -50   │    │
  │  │ 现金      │ 3,100   │ 3,100   │ 0     │    │
  │  │ 银行卡    │ 5,000   │ 4,970   │ -30   │    │
  │  │ 合计      │ 28,800  │ 28,640  │ -160  │    │
  │  └──────────────────────────────────────┘    │
  │  差异率 0.56% ✅ 在正常范围(0.5-0.6%)       │
  └──────────────────────────────────────────────┘
```

### 3.2 全渠道利润分析

这是老板最关心的——**到底哪个渠道赚钱？**

#### 统一利润模型

```typescript
interface ChannelProfit {
  channel: ChannelType;
  channelSource: string;
  
  // 收入端
  grossRevenue: number;        // 总销售额（含税）
  refundAmount: number;         // 退款金额
  netRevenue: number;           // 净收入
  
  // 商品成本
  productCost: number;          // 商品销售成本
  
  // 渠道费用
  platformFees: number;         // 平台费用（佣金+广告+服务费）
  paymentFees: number;          // 支付手续费
  shippingCost: number;         // 物流成本
  marketingCost: number;        // 营销费用
  
  // 其他成本（可按比例分摊）
  laborCost: number;            // 人工分摊
  rentCost: number;             // 租金分摊
  overhead: number;             // 其他运营费用
  
  // 利润结果
  grossProfit: number;          // 毛利 = netRevenue - productCost
  grossMargin: number;          // 毛利率
  channelContribution: number;  // 渠道贡献 = grossProfit - 渠道专属费用
  netProfit: number;            // 净利润 = 扣减所有分摊后
  netMargin: number;            // 净利率
}
```

### 3.4 全渠道统一税务口径

不同渠道的销售额合并统计用于税务申报：

```
📱 线上平台 (京东/天猫/抖音/视频号)
  → 各平台结算单中的"销售额合计"
  → 增值税: 一般纳税人 13%/6%/9%, 小规模 1%
  → ⚠️ 注意: 平台已代扣代缴的服务费部分

💬 私域自营 (小程序)
  → 微信商户收款总额
  → 增值税: 同线上
  → 自行申报全部销售额

🏭 线下批发
  → 开票销售额 (增值税发票系统)
  → ⚠️ 注意: 未开票收入也需要申报

🏪 线下零售
  → POS 系统的含税销售额
  → 增值税: 同上

📊 汇总
  ┌──────────────────────────────────────────┐
  │  本月应税销售额汇总                        │
  │                                          │
  │  线上平台 (已签收): ¥3,200,000            │
  │  私域自营:       ¥800,000                 │
  │  线下批发 (开票): ¥2,100,000              │
  │  线下零售:        ¥1,000,000              │
  │  ────────────────────────────────────     │
  │  合计应税销售额:   ¥7,100,000              │
  │  销项税额:         ¥923,000 (13%)          │
  └──────────────────────────────────────────┘
```

**关键设计**：系统自动汇总各渠道数据，但允许用户**手动调整**每个渠道纳入税务统计的销售额（因为可能存在退货尚未处理、或折扣口径不同的问题）。

## 八、和"只做线上平台"方案的关键差异

| 维度 | 纯线上平台方案 | 混合渠道方案（本方案） |
|------|-------------|-------------------|
| **对账模型** | 二维（订单↔资金） | 四模式（各渠道各自对账规则） |
| **收入确认** | 签收确认（统一） | 各渠道不同规则（可配置） |
| **利润分析** | 平台维度 | 渠道类型+具体来源+全渠道汇总 |
| **新增模块** | 无 | 应收账款管理、客户对账单、账龄分析 |
| **导入模板** | 仅平台账单 | 平台+批发模板+零售日报模板 |
| **AI 重点** | 平台费用分析 | 全渠道利润对比 + 渠道效率分析 |
| **产品导航** | 按功能分 | **按渠道+功能双重维度** |
| **用户配置** | 较少 | 渠道配置向导（首次使用） |
| **价值主张** | 帮电商对账 | **帮多渠道企业看清楚"到底哪里赚钱"** |

## 九、用户验证要点

MVP 阶段邀请内测用户时，重点关注：

1. **渠道覆盖度验证**：用户的渠道组合是否符合我们的四类划分？有无遗漏？
2. **导入易用性**：用户是否能顺畅地从各平台导出数据并上传？
3. **批发模板的通用性**：批发客户的格式差异大，模板是否能覆盖大部分场景？
4. **全渠道利润的准确性**：用户是否能接受"系统自动计算的全渠道利润"并信任它？
5. **最大价值模块**：用户用得最多的功能是什么？对账？利润分析？还是应收管理？

---

## 十、总结

中小电商企业的现实是：**他们不在单一平台上做生意，他们在全渠道上做生意。**

他们的核心财务痛点是三个"对不上"：
1. **资金对不上**——各渠道收入 vs 银行到账
2. **利润对不上**——各渠道赚的钱合不到一起算
3. **客户对不上**——批发客户的应收账款管不住

FinSight 的混合渠道 MV P 通过 **"统一的交易模型 + 四类渠道适配器 + 全渠道利润汇总"** 来解决这三个问题，让企业的财务从"每个渠道各算各的"变成"全渠道一个数"。
